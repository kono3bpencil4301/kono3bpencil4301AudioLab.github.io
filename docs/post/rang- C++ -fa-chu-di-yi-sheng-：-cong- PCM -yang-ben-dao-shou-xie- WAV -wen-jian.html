让 C++ 发出第一声：从 PCM 样本到手写 WAV 文件

作为一个电子音乐爱好者，同时也作为一个准程序员，我总想手搓出一台合成器，借此机会，我向大家从音频学的底层讲起，结合C++语言原生库，不依赖任何第三方音频框架，从零开始手搓出合成器。

C++这门语言就不必多介绍了，这里先介绍计算机是怎么理解声音的，想象下，一个声音在现实当中，是不是通过空气等媒介压力变化，通过声源振荡产生的。这也是现实发声的原理，而在计算机的世界中，声音通常将振荡的波通过离散的数字序列储存起来，而这里也引出一系列的概念。

音频基础概念

采样点

由于计算机音频采用的是离散的数字序列，因此在一段音频当中，每隔一段时间取得的一个数值样本，用于记录该时刻，声音信号的振幅大小，这个点代表的数值叫做采样点。也就是

$$ x[n]=x(nTs) $$

采样点是数字音频最基础的数据单元，像一台高速相机，每秒拍摄几万张声波的声波振幅的高度照片。

采样率

采样率在计算机的语言当中，以多快的频率来记录，单位为Hz。采样率决定数字系统能够表示的最高频率范围，但对应的文件大小也就越大。而根据奈奎斯特采样定理：

$$ fs​>2fmax​ $$

且由于人耳可听范围约20Hz~20kHz，根据奈奎斯特采样定理，需要超过40kHz采样率，因此44.1kHz成为消费音乐领域的重要标准，而影视级别的则略高于CD级别的，为48000Hz。

位深

如果采样率记录的是声波在时间维度方面的信息，那么位深则是记录了一段音频中，采样点的纵向动态程度。位深表示每一个采样点使用多少二进制位进行存储，它决定振幅量化的精度。位深越高，每个采样点能够表示的振幅等级越多，动态范围也越大。而由于计算机采用二进制，因此位深的单位为Bit。

8bit位深，对应的等级范围是-128~127，而16bit则是−32768∼32767。CD 音频标准采用 16bit/44.1kHz PCM。

关于量化误差和动态范围

由于原来声音是连续的信号，因此在量化的时候，若单纯量化的Bit数值不够大，会导致原始声音无法完全落在整数等级上，因此会产生微小的误差，从而导致同一段声音信号，对饮8bit音频信号，和16bit听感上，前者要粗糙，而后者会更加平滑。

声道

如果前面三个负责回答声音怎么储存起来，那么声道回答：

一个采样点到底代表一个声音，还是多个声音。

在现实中，单声道通常由一个麦克风录入声源的声音信息，然后通过扬声器输出。而立体声则是两个甚至多个音频输入参与录制，最后通过多个扬声器进行输出。

在声道中，分为单声道和多声道，单声道每隔时间点只记录有一个振幅x[n]，而多声道则记录有两个甚至多个。在音频界当中，还有音频帧的概念，也就是一个音频帧，代表着某一个时间瞬间所有声道的采样集合。

比如，在44100Hz的双声道的情况下，每一秒音频，存在44100个Frame，而不是88200Sample。

PCM

那相信各位得知时间怎么采样，振幅怎么量化，声音怎么量化了之后，这些数字信号，到底如何排列呢，这里就牵扯出一个概念，PCM（Pulse Code Modulation，脉冲编码调制），PCM是一种将连续模拟信号转换为数字信号的方法，其过程包括采样、量化和编码三个步骤。PCM最早由Alec Reeves于1937年提出，后来随着数字信号处理技术发展，成为现代数字音频存储的基础。

而PCM的大致流程如下

麦克风负责捕捉空气压力的变化，然后麦克风将变化转换为模拟电信号，之后计算机负责对电信号进行采样、量化和编码，最后数据以PCM的数据储存起来。

在C++的代码语言中，就是将double value 转换为int16_t sample，也就是浮点振幅转换为PCM整数。

顺便我们也可以得出公式，用于计算Wav文件的数据量大小，即

$$ ByteRate=SampleRate×Channels×BitsPerSample/8 $$

注意这个8，意思是计算机将Bit（比特）数据转换为储存的基本单位，即Byte（字节）。1Byte=8Bit。

让我们来计算下，在CD音质下（44100Hz，双声道，16bit），一分钟的Wav音频，大小为44100×2×16/8*60=10,584,000 字节，大约为10MB。

关于Wav文件格式

那么PCM是里面的数据，总得要个容器得包装起来吧，就像一杯牛奶，里面的牛奶是PCM数据，而Wav格式则是这个杯子。同样，后面视频中的MP4这个格式也是杯子，真正的牛奶则是H264之类的编码。

那RIFF结构，则是描述Wav格式的结构标准，它负责描述杯子，这个杯子是玻璃杯，还是纸杯，这个杯子的形状，颜色等等。

在RIFF结构当中，包含以下的结构块：

RIFF Chunk
|
├── "RIFF"
├── File Size
├── "WAVE"
|
├── fmt Chunk
│      ├── Format
│      ├── Channels
│      ├── Sample Rate
│      └── Bits
|
└── data Chunk
       └── PCM Samples

注意fmt后面必须有一个空格，否则不满足Chunk必须占四个字符的要求，从而会导致输出的文件出错。

不过在正式动手写Wave文件时，还需要理解个概念——小端序。

关于小端序

要想了解小端序，我们先进行32位整数的讲解，计算机并不是以十进制数字保存数据，而是按照字节存储。当一个数字超过一个字节时，就需要规定多个字节之间的排列顺序。如一个 32 位整数：

0x12345678

它是由4个字节组成的，即12 34 56 78，这其中12由于离0x最近，因此是最高有效字节，而78里0x最远，因此是最低有效字节，大端序就是从最高有序字节往最低读，自然，小端序则是最低往最高读了，也就是78 56 34 12了。

RIFF最初是由微软提出的，而微软早期的x86系统长期采用小端序，所以Wav规定所有整数全部采用小端序。在x86体系中，基本都是小端环境，但在网络协议，以及一些嵌入式系统和古早架构中，则是使用大端序。

WAV Header：音频文件的入口

到这里，我们已经知道 PCM 是声音数据本身，但是如果直接把 PCM 数字写入硬盘，播放器并不知道这些数字代表什么。就像你那糟糕的上司，你给一堆公司的数据，他可能看不懂，因此还得动用你的废话文学去讲述公司雪上加霜的财报数据。

计算机也需要那些”废话文学“（好吧，Header并不废话），于是计算机需要一个文件头，告诉播放器下属”我会如何处理这些数据的“

也就是

WAV文件
├── Header
└── PCM Data

Wav Header的结构

RIFF Header

在一个经典的PCM Wav当中，Header是44字节，因此，文件大小满足如下的表达式：

文件大小 = PCM数据 + 44 bytes

C++语言编写实战

代码数据结构设计

在C++语言当中，我们定义一个Wave Format结构体，进行C++的数据结构对Wav文件中的元数据的映射：

struct WaveFormat
{
    uint16_t channels;
    uint32_t sampleRate;
    uint16_t bitsPerSample;
};

然后，我们再规定个结构体，Chunk：

struct Chunk
{
    uint32_t id;
    uint32_t size;
};

编写二进制写入函数

**RIFF 格式使用 Four‑CC 四字符码做块标记，强制占 4 字节，方便二进制直接偏移读取，简化解析逻辑。**在这里，我们使用WriteFourCC的函数进行操作：

// 写入 4 字节的 FOURCC 标识（直接按字节写入，无需考虑大小端）
void WriteFourCC(std::ostream& out,std::string_view text)
{
	if (text.size() != 4)
        throw std::invalid_argument("text must be 4 characters long");
    out.write(text.data(), 4);    
}

这里再次注意，fmt后面要紧跟着空格，这样才符合四字节的要求。

而小端序部分，我们这里创立了两个函数WriteU16LE和WriteU32LE，对这里面的数据进行字节的拆解

// 写入 16 位无符号整数（小端序：低字节在前）
void WriteU16LE(std::ostream &out, uint16_t value)
{
    const char byte[2] = {static_cast<char>(value & 0xFF), static_cast<char>(value >> 8)};
    out.write(byte, 2);
}

// 写入 32 位无符号整数（小端序：低字节在前）
void WriteU32LE(std::ostream &out, uint32_t value)
{
    const char byte[4] = {static_cast<char>(value & 0xFF), static_cast<char>(value >> 8), static_cast<char>(value >> 16), static_cast<char>(value >> 24)};
    out.write(byte, 4);
}

让正弦波粉墨登场

WAV 文件结构已经准备完成，接下来缺少最后一个东西：PCM 数据。这里我们拿最简单的正弦波举例，正弦波的连续信号为

$$ x(t)=Asin(2πft) $$

而转换为离散的数字信号，则是：

$$ x[n]=Asin(2πfn/fs​) $$

对应代码，则是

double value = amplitude * sin(phase);

相位累加器：从正弦波到 Oscillator

相位累加器是当代数字振荡器的核心，它解释了，如何让一个正弦波，到发出声响的振荡器，毕竟，每次到一个采样点，都得重新计算sin(2pif*t)效率很低，因此我们可以考虑计算完当前phase后，每次增加

$$ \Delta\phi = \frac{2\pi f}{f_s} $$

对应代码实现如下：

double phase = 0.0;
    // 每帧的相位增量 = 2π × 频率 / 采样率
    const double phase_step = 2.0 * PI * frequency / sampleRate;
    for (uint32_t i = 0; i < frame_count; ++i)
    {
   //......
   // 累加相位，保持在 [0, 2π) 范围内防止浮点精度随时间劣化
        phase += phase_step;
        if (phase > 2.0 * PI)
            phase -= 2.0 * PI;
            }

就实现了最基础的数字振荡器。后续的Saw、Square、Triangle等波形，本质上也会复用相位累加器，只是改变相位到振幅的映射方式。

浮点转PCM

将连续信号的浮点数据值，转换为符合PCM样式的数值，也就是在振幅为1的情况下，将-1.0 ~ 1.0的振幅转换成-32768 ~ 32767。因此sample = value * 32767

Why C++？？

选择 C++ 并不是因为它比其他语言“高级”，而是因为音频程序处于一个特殊领域：它需要同时连接数学算法、内存数据和硬件设备。C++ 在性能、控制能力和音频生态之间取得了较好的平衡，因此成为实时音频开发领域最常见的语言之一。

Python不是不行，它依赖第三方库，非常适合音频分析，AI音频，数据处理等等，但，这个系列的最终核心，是实现一个实时合成器，Python的底层性能问题是不能忽视的。C语言接近硬件，性能高，简单直接，但C语言面向复杂工程，尤其是后续写一个完整的合成器，其没有Class的面向对象的属性就难以适配大型工程。而Java是生态问题，Java在大家刻板印象中，更适合企业后端，大型引用。但对实时音频而言，不可预测的GC暂停可能增加实时处理风险，对于网页，几十毫秒的暂停都没关系，但对于实时音频，突然暂停就可能出现大问题了，所以专业音频底层一般不会选择 JVM。
